# Дополнения к проекту

Здесь лежит только новый код. Исходные файлы проекта (`src/`, `include/`, `CMakeLists.txt`,
`README.md`) не менялись. Изменён только `bench.cpp` в корне — он теперь сравнивает все методы.

## Сборка и запуск

Нужны CMake и компилятор C++17 (на Mac — Xcode Command Line Tools). Из корня проекта:

```bash
cmake -S extensions -B build-ext
cmake --build build-ext

./build-ext/ext_tests                                         # проверка всех методов (~3 с)
./build-ext/text_verification_ext                             # ввод с клавиатуры, как в исходной программе
./build-ext/text_verification_ext extensions/examples/kb2.txt # база из файла, все 7 методов
./build-ext/text_verification_ext extensions/examples/kb1.txt 7   # только вывод из аксиом
cd build-ext && ./bench                                       # бенчмарк, пишет bench_results.csv
```

Сборка по умолчанию идёт с оптимизацией (`Release`) — иначе замеры времени не имеют смысла.

Файл с базой знаний: предложения по одному в строке, пустая строка, затем запрос.
Примеры — в `extensions/examples/`: `kb1.txt` (Иван), `kb2.txt` (13 предложений с «не»),
`kb_or.txt` (база с «или»), `kb_not_follows.txt` (запрос не следует).

## Что добавлено

### 7. Вывод из аксиом: A1–A3, A∀, MP, теорема о дедукции (`src/hilbert.cpp`)

Связь с ЛЗ2. База знаний превращается в посылки исчисления:

* клауза `L1 ∨ … ∨ Ln` записывается как `¬L1 → (¬L2 → … → Ln)` — так же, как в ЛЗ2 `A∨B = ¬A→B`;
* правило с переменной — формула с квантором: `∀x(Student(x)→(Passed(x)→Credit(x)))`;
* аксиома исчисления предикатов `A∀: ∀x F(x) → F(t)` (4° из лекции) подставляет конкретное имя.

Сначала строится вывод запроса из посылок только по A∀ и MP — это прямой вывод,
где каждый шаг записан строкой вывода:

```
1. Student(иван)                                     [посылка]
2. Passed(иван)                                      [посылка]
3. ∀x(Student(x)→(Passed(x)→Credit(x)))              [посылка]
4. ∀x(…)→(Student(иван)→(Passed(иван)→Credit(иван))) [A∀, x := иван]
5. Student(иван)→(Passed(иван)→Credit(иван))         [MP 3, 4]
6. Passed(иван)→Credit(иван)                         [MP 1, 5]
7. Credit(иван)                                      [MP 2, 6]
```

Потом по теореме о дедукции посылки снимаются одна за другой (тот же алгоритм, что в задании 2
ЛЗ2: каждая строка заменяется тремя, строка-посылка — пятью). Получается теорема
`⊢ γ1 → (γ2 → … → запрос)`, выведенная только из аксиом. Оба вывода проверяются функцией
`hil::check`, полный вывод пишется в `hilbert_proof.txt`.

Ограничение: используется только MP, без разбора случаев и лемм из ЛЗ2, поэтому база с «или»
(`kb_or.txt`) этим методом не доказывается, хотя запрос из неё следует. Для полноты нужно
перенести алгоритм ЛЗ2 (от противного + разбор случаев + леммы Л1–Л7).

### 4. Резолюции v2 (`src/resolution_sos.cpp`)

* Стратегия «множество поддержки»: резольвируются только пары, где хотя бы одна клауза
  произошла от отрицания запроса. Первыми берутся короткие клаузы.
* Резольвенты, которые поглощаются уже имеющимися клаузами, отбрасываются.
* Запоминается, из каких клауз получена каждая резольвента, — печатается вывод пустой клаузы
  с подстановками (унификацией).

Зачем: исходные резолюции перебирают все пары подряд и на цепочке из 20 студентов
упираются в лимит 20 000 пар. Версия v2 доказывает и N = 80.
Оговорка: стратегия полна, если сама база непротиворечива (тест это учитывает).

### 5. Прямой вывод v2 (`src/forward_unit.cpp`)

Исходный прямой вывод на базе с «не» отвечает «не поддерживается». Здесь запоминаются
и положительные, и отрицательные факты: если в клаузе все литералы кроме одного ложны,
оставшийся выводится. Для правил Хорна это тот же прямой вывод. Корректен, но без разбора
случаев не выводит всё, что следует из баз с «или».

### 6. Таблицы v2 (`src/tableau_clausal.cpp`)

Исходные «таблицы» после подстановки констант ветвятся по значению переменной (true/false) —
по сути это DPLL. Здесь ветвление как в аналитических таблицах: невыполненная клауза
`L1 ∨ … ∨ Lk` делит ветвь на k ветвей (β-правило для «или»), ветвь закрыта, если в ней есть
X и ¬X. Программа печатает дерево.

### Тесты (`tests/tests.cpp`)

На 4000 случайных базах проверяется:
* исходные резолюции, резолюции v2 и таблицы v2 дают тот же ответ, что исходные таблицы;
* прямой вывод v2 и вывод из аксиом ничего лишнего не доказывают;
* на базах Хорна прямой вывод v2 совпадает с исходным;
* каждый вывод из аксиом (и с посылками, и после теоремы о дедукции) проходит проверку;
* проверка ловит испорченный вывод.

Найдено попутно: исходный `forwardChaining` ничего не выводит из факта с переменной
(`∀x P(x)`). Парсер таких фактов не создаёт, поэтому на работу программы это не влияет.

## Что показывает бенчмарк

* На маленьких базах все методы укладываются в десятки микросекунд, исходные резолюции —
  самые медленные (перебор всех пар).
* На цепочке из N студентов исходные резолюции с N = 20 упираются в лимит, резолюции v2 —
  нет. Таблицы и прямой вывод растут плавно.
* Вывод из аксиом по длине: из посылок — около 2N строк, а после снятия посылок по теореме
  о дедукции — уже 24 000 строк при N = 5 и больше 300 000 при N = 10. Каждая снятая посылка
  примерно утраивает вывод — то же, что в ЛЗ2 (A9: 19 → 1268 строк).
